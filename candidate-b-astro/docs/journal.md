  (`data-galleryReady`), поэтому второй экземпляр на сайте не добавляет
  ни новых скриптов, ни новых правил в политику
- слайдер рендерится только при `gallery.length > 0`
- `src/components/sections/PhotoWall.astro` — вариант «фото-стена» на CSS
  Grid, без подписей и без JavaScript. Написан первым, в разметке не
  используется, оставлен в репозитории сознательно: если слайдер когда-нибудь
  окажется лишним, переключение обратно — это одна строчка импорта. Astro
  собирает только то, что импортировано, так что на бандл он не влияет

- 14 настоящих фото со слайдера оригинала забраны и лежат в
  `src/assets/team/wall-01…14.jpg`. Достать их curl'ом со страницы нельзя:
  Webflow подставляет `src` слайдов скриптом, в отданном HTML пустые `<img>`.
  Снимали из живого браузера — сниппет для консоли записан в
  `scripts/fetch-assets.sh`
- у `Gallery.astro` появился необязательный проп `widths` (по умолчанию
  прежний `[480, 800, 1200]`). /company передаёт `[480, 720, 960]`: исходники
  слайдера ровно 960px, больше Webflow не отдаёт, а запрос 1200 заставил бы
  Astro растянуть картинку — файл тяжелее, деталей не прибавилось. /games с
  его артами по 5670px не затронут
- alt у каждого слайда описывает конкретный кадр, а не повторяет одну фразу
  14 раз; имён сотрудников в alt нет
- у `Gallery.astro` появились точки-индикаторы, как `slide-nav` у оригинала:
  сколько всего фото и где ты сейчас — на это стрелки не отвечают. Разметку

  только в `aria-current`, и стиль селектится по нему — второго класса,

  слайда одновременно, и «виден ли элемент» не может назвать один текущий
- обработчик прокрутки дросселируется через `requestAnimationFrame`: scroll

## 04.09 — автодеплой Cloudflare отключён

Первый же pull request показал красный крест от бота
`cloudflare-workers-and-pages`. Логи сборки:

```
Executing user build command: npm run build
npm error path /opt/buildhome/repo/package.json
npm error enoent Could not read package.json
```

Интеграция запускала `npm run build` в корне репозитория, где `package.json`
нет вообще: в корне лежит Go-кандидат, а этот проект — в `candidate-b-astro/`.
Корневая папка в настройках указана не была, поэтому сборка падала на любом
пуше в любой ветке. То есть интеграция не работала ни разу, а сайт живой
потому, что деплой всё это время делался руками.

Вторая проблема ждала следующей очереди: `Build variables: None`, а в
`astro.config.mjs` стоит `validateSecrets: true` и обязательный
`TURNSTILE_SECRET`. Починка корневой папки просто передвинула бы падение на
шаг вперёд. GitHub Actions этот секрет подставляет явно (тестовый ключ
Turnstile, `ci-astro.yml`, строки 28–38) — сборщик Cloudflare о нём знать не
мог, `.dev.vars` в `.gitignore`.

Решение: интеграцию отключить. Обе настройки, которые её бы вылечили —
корневая папка и build-переменная — живут в дашборде, то есть это две
единицы конфигурации сборки, невидимые в ревью. Прямо против собственного
правила проекта «platform configuration lives in the repo». Плюс она
публиковала по пушу, а хотелось решать самой, когда версия становится
показываемой.

- добавлен скрипт `npm run deploy`: подставляет `BUILD_SHA` и запускает
  `wrangler deploy`. Раньше это была команда, набираемая по памяти, и забыть
  `BUILD_SHA` означало бы, что `/api/health.json` врёт про версию
- запрет на повторное подключение записан в `AGENTS.md`, в раздел
  «Do not do this», вместе с причиной — иначе через месяц это выглядит как
  просто неподключённая интеграция
- взамен появился `.github/workflows/deploy.yml`. Он делает то же, что должна
  была делать интеграция, но правила публикации лежат в репозитории и их
  можно прочитать: только `main`, только после `format:check`, `check`,
  `test` и `build`, плюс кнопка ручного запуска (`workflow_dispatch`) —
  она нужна, чтобы переопубликовать текущий `main` без нового коммита,
  например после ротации секрета через `wrangler secret`
- `concurrency` с `cancel-in-progress: false`: два `wrangler deploy` в гонке
  могли бы завершиться не в том порядке и оставить в проде более старую
  сборку. Очередь медленнее и правильнее
- проверки в `deploy.yml` продублированы, а не унаследованы через
  `workflow_run`. Сознательно: `workflow_run` переносит деплой в другое
  событие, у которого ref — не тот, что публикуется. Минута повторного CI
  в обмен на файл, который сверху вниз говорит, что должно пройти перед
  публикацией
- токен Cloudflare лежит в GitHub Secrets и подставляется только в шаг
  деплоя, а не на весь job
